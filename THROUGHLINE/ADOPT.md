# ADOPT.md

이미 개발이 진행 중인 프로젝트(브라운필드)에 이 프레임워크를 **적용(채택)** 하기 위한 프롬프트입니다.

`KICKOFF.md`가 "요구사항에서 앞으로 만든다(greenfield)"라면,
`ADOPT.md`는 **"이미 있는 코드에서 역방향으로 문서를 만든다(brownfield)"** 입니다.

목적은 실제 구현이 아니라, **기존 코드베이스의 현재 상태를 정확히 문서화**하여
이후 `DEVELOPINIT.md`로 개발을 이어갈 수 있는 운영 문서·횡단 계약·기능명세·QA·개발 계획을 갖추는 것입니다.

> 산출물 구조는 `KICKOFF.md`와 **완전히 동일**합니다(아래 1절). 따라서 채택이 끝나면
> 그 이후 개발은 `DEVELOPINIT.md`를 greenfield와 똑같이 사용합니다.

> **경로 기준:** 프레임워크 산출물은 루트 3파일(프로젝트 `README.md`, `AGENTS.md`, `CLAUDE.md`)을 제외하고
> 모두 **`THROUGHLINE/` 폴더 안**에 생성합니다. 이 문서의 산출물 경로는 모두 `THROUGHLINE/` 기준입니다.
> 덕분에 기존 프로젝트의 `docs/` 등 동명 폴더와 충돌하지 않습니다 — **기존 프로젝트 폴더를 키트 산출물로 병합하려 하지 마세요.**

> **재채택 금지:** `THROUGHLINE/` 폴더가 이미 존재하고 산출물이 들어 있는 프로젝트는 **이미 채택된 프로젝트**입니다.
> ADOPT를 다시 실행하지 말고, `THROUGHLINE/PROGRESS.md`를 확인해 이어가거나 사용자에게 확인하세요.

# 0. KICKOFF.md와의 관계 (중복 방지)

이 문서는 **브라운필드 고유 동작**만 규정합니다.
문서 작성의 **세부 규칙은 `KICKOFF.md`의 해당 절을 그대로 따릅니다.** (두 벌로 복제하지 않습니다.)

# 2. 브라운필드 핵심 원칙

1. **코드가 현재의 사실(authority for as-built)입니다.**
   명세는 먼저 코드의 실제 동작을 정확히 기술한 뒤, "의도와의 괴리"는 별도로 표시합니다.
   구현 실수를 명세로 둔갑시키지도, 그렇다고 코드를 임의로 "옳다"고 단정하지도 않습니다.
2. **코드를 실제로 읽습니다(메타데이터 스캔으로 끝내지 않습니다).**
   파일 목록·폴더 구조·이름만 훑고 동작을 추측하지 말고, 진입점부터 각 기능의 실제 구현·핵심 경로를
   **직접 읽고 동작을 추적**한 뒤에 명세를 작성합니다. as-built 명세는 "읽은 코드"에 근거해야 합니다.
3. **추측 금지(no-hallucination).** 직접 읽고 확인한 것만 단정합니다.
   읽지 않은 코드의 동작을 파일명·구조로 추측해 명세로 적지 않습니다.
   추론에 그쳤거나 코드에서 확정하지 못한 컨벤션·계약·의도는 `ASSUMPTIONS.md`에 `상태: active`(검증 필요)로
   기록하고 채택 보고서의 "검토 권장"에 모읍니다.
4. **기존 파일 비파괴.** 이미 있는 `README.md`, `AGENTS.md`, `CLAUDE.md`, `.gitignore`, `docs/` 등은
   덮어쓰지 않고 병합하거나 diff를 제시한 뒤 확인을 받습니다(5절).
5. **이 단계에서는 코드를 수정하지 않습니다.** ADOPT는 문서화·계획 수립 단계입니다.
   발견한 버그·악취·괴리는 기록만 하고, 실제 수정은 `DEVELOPINIT.md` 단계로 넘깁니다.
6. **테스트는 실제 실행해 baseline을 만듭니다.** "통과 주장"이 아니라 실행 결과(통과/실패/부재)를 기록합니다.

# 3. 입력

* **기존 코드베이스 (필수).** 채택의 1차 입력입니다.
* **`SOURCES/REQUIREMENTS.md` (선택, 권장).** 있으면 "앞으로의 목표·제약·미구현 요구사항"으로 사용하고,
  as-built와 교차검증합니다. 없거나 비어 있으면 현재 상태 문서를 코드에서 만들고, 앞으로의 방향은 필요한 만큼만 질문합니다.
  (brownfield에서 이 문서의 유형은 동일하게 `초기 요구사항`이며, 채택 완료 시 `반영 완료`로 동결됩니다.)
* **기존 문서 (있으면).** 기존 `README.md`/위키/주석 등은 의도 파악의 보조 입력으로 흡수합니다.

# 4. 채택 작업 순서

채택은 단계가 길어 끊길 수 있습니다. **각 단계가 끝날 때마다 `PROGRESS.md`의 채택 진행 상태를 갱신**하세요.
중단되면 다음 세션은 `PROGRESS.md`를 읽고 끊긴 지점부터 이어서 진행합니다.

1. **기존 산출물 인벤토리.** 먼저 `THROUGHLINE/`에 기존 산출물이 있는지 확인합니다
   (있으면 재채택 금지 — 머리말 참조). 다음으로 루트의 README.md / AGENTS.md / CLAUDE.md / .gitignore 중
   이미 존재하는 것을 식별하고, 보존·병합 계획을 세웁니다(5절).
   기존 프로젝트의 docs/ 등 동명 폴더는 키트 산출물과 무관하므로 건드리지 않습니다.
2. **코드베이스 스캔(바깥 지도).** 언어·런타임·프레임워크, 빌드/실행/테스트 명령, 디렉토리 구조, 진입점,
   의존성, 환경변수 **이름**(값/Secret은 절대 수집·기록 금지)을 파악합니다.
   (이 단계는 **메타데이터 지도**입니다. 여기서 멈추지 말고 3단계로 코드를 실제로 읽으세요.)
3. **기존 코드 정독(리뷰).** 진입점에서 시작해 주요 기능의 **실제 구현·핵심 경로를 직접 읽고 동작을 추적**합니다.
   라우팅/핸들러/서비스/데이터 접근/외부 연동/인증 경로 등 **동작을 결정하는 코드**를 우선 읽습니다.
   * 이후 단계(4 컨벤션·5 명세·9 ADR)는 **여기서 읽은 코드에 근거**해야 합니다.
   * 파일명·폴더·이름만 보고 동작을 추측하지 않습니다(2절 원칙 2·3).
   * 코드가 방대하면 임의로 일부만 보고 "다 봤다"고 하지 말고, **읽은 범위와 읽지 못한 범위를 명시**합니다.
     읽지 못한 영역은 `PROGRESS.md`에 남겨 다음 세션이 이어 읽도록 합니다.
4. **횡단 컨벤션 역추출 → `ARCHITECTURE.md` 초안.** 읽은 코드에서 실제로 쓰인
   네이밍(DB/변수/파일/API 경로), API 계약 스타일·에러 포맷, 인증/세션 방식, 데이터 모델 공통 규칙을
   탐지해 기록합니다. 코드에서 확정할 수 없는 항목은 `ASSUMPTIONS.md`(active)로 남깁니다.
   (포함 내용은 `KICKOFF.md` 7절을 따르되, "정한다"가 아니라 "탐지·확정한다"로 해석합니다.)
5. **구현된 기능 식별 및 as-built 명세화.** 읽은 코드에서 기능 단위를 분해(입도 가이드 `KICKOFF.md` 6.0)하고,
   각 기능을 **현재 동작 그대로** `features/*.md`(구조 `KICKOFF.md` 6.1)에 작성합니다.
   * **근거 코드 표기(정확성 점검):** 명세의 각 동작 주장은 근거가 된 코드 위치(파일/함수)를 댈 수 있어야 합니다.
     직접 읽지 않은 동작은 단정하지 말고 "추정(검증 필요)"으로 표시합니다(2절 원칙 3).
     가능하면 해당 경로를 실제 실행하거나 테스트로 **교차검증**합니다.
   * 코드↔의도 괴리, 죽은 코드, 미완성 기능, 의심 지점은 해당 feature 문서 **15절(미결정)** 과
     `ASSUMPTIONS.md`에 기록하고, 판단 불가하면 6절에 따라 질문합니다.
   * 비자명한 기능은 `KICKOFF.md` 4.1에 따라 최소 검토 요약(참여 Agent·주요 위험)을 남깁니다.
6. **미구현/계획 식별.** `SOURCES/REQUIREMENTS.md`가 있으면, 거기 적힌 요구사항 중 코드에 아직 없는 것을
   "남은 작업"으로 분류합니다. as-built와 충돌하는 요구사항은 6절에 따라 질문합니다.
7. **테스트 baseline.** 기존 자동 테스트를 **실제 실행**하고 결과(실행 명령 + 통과/실패/부재)를 기록합니다.
   실패·부재 항목은 `HISTORY.md`/`PROGRESS.md`와 `qa/` 문서에 현재 커버리지로 반영합니다.
8. **QA 문서 작성** (`KICKOFF.md` 8절). 단, 이상적 기준이 아니라 **현재 커버리지 현실**을 먼저 반영하고,
   부족한 부분은 "보강 필요"로 표시합니다.
9. **소급 ADR(선택).** 현재 코드에 이미 반영된 중요한 설계 결정(아키텍처/인증/DB/외부 API/배포 등)은
   필요한 핵심만 소급 ADR로 기록하고 `adr/INDEX.md`를 만듭니다. 과도하게 만들지 마세요.
10. **`ARCHITECTURE.md` 확정**, **프로젝트 `README.md` 작성/병합**(`KICKOFF.md` 7.1, 기존 있으면 5절).
11. **`AGENTS.md` / `CLAUDE.md` 작성/병합**(`KICKOFF.md` 9·11절, 기존 있으면 5절).
12. **`PLAN.md`** 작성: Phase를 **완료(기존 구현) / 진행 중 / 남은 것**으로 현재 상태를 반영합니다.
13. **`PROGRESS.md`** 작성: 현재 상태를 seed하고 **다음 세션 첫 명령**을 기록합니다.
14. **`HISTORY.md`** 작성: 첫 항목을 "프레임워크 채택(ADOPT)"으로 두고 테스트 baseline·괴리 목록을 기록합니다.
15. **`ASSUMPTIONS.md`** 작성: 역추출 추정과 검증 필요 항목을 기록합니다.
16. **`NOTES.md`** 작성(`KICKOFF.md` 15.1): 코드 정독 중 **확인한** 비자명한 사실
    (문서화되지 않은 외부 API 동작, 환경 함정, 성능 특성)을 주제별로 기록합니다.
    확인하지 못한 추측은 NOTES가 아니라 ASSUMPTIONS에 둡니다.
17. **`SOURCES/INDEX.md`** 생성/갱신(`KICKOFF.md` 15.2).
    `SOURCES/REQUIREMENTS.md`가 있으면 유형 `초기 요구사항`으로 등록하고 채택 완료 시 `반영 완료`로 동결합니다.
    기존에 흩어져 있는 요구사항·스펙 문서를 SOURCES/로 옮겨 등록할지는 사용자 확인 후 수행합니다
    (5절 비파괴 원칙 적용 — 임의로 이동하지 않습니다).
18. **채택 산출물 commit.** 채택은 작업 브랜치(예: `docs/throughline-adopt`)에서 수행합니다 — 이미 동작하는 코드가 있는 프로젝트이므로 main/master에서 직접 작업하지 않습니다. 생성/병합한 문서를 하나의 commit으로 묶습니다(여러 세션에 걸치면 중간 지점 commit 허용). 이 commit에는 문서만 포함하고 코드 변경은 넣지 않습니다(2절 원칙 5). push는 push 정책(기본: commit만)을 따릅니다.
19. **채택 완료 보고**(7절 형식).

# 5. 기존 파일 병합 규칙 (중요)

키트 산출물이 THROUGHLINE/ 안에 격리되므로, 병합 대상은 사실상 **루트 4개**
(`README.md`, `AGENTS.md`, `CLAUDE.md`, `.gitignore`)뿐입니다. 이들이 이미 존재하면 **덮어쓰지 않습니다.**
기존 프로젝트의 `docs/` 등 동명 폴더는 키트 산출물(THROUGHLINE/docs/)과 별개이므로 병합·수정하지 않습니다.

* 기존 내용을 **보존**하는 것을 우선합니다. 보존의 대상은 자구가 아니라 **의미(규칙·정보)** 입니다.
* 프레임워크가 요구하는 항목이 빠져 있으면 **추가(병합)** 합니다.
* **병합 결과물의 서술 산문도 언어 기준(KICKOFF.md 머리말)을 따릅니다.**
  기존 내용이 다른 언어로 적혀 있으면 의미를 보존해 규정 언어로 번역하여 병합하세요 —
  언어가 섞인 채 이어 붙이면 그 파일(특히 매 세션 자동 로드되는 CLAUDE.md)이 영어 표류의 점화 신호가 됩니다.
  (코드 식별자·고유명사·`.gitignore`는 번역 대상이 아닙니다.)
* 기존 내용과 프레임워크 규칙이 충돌하면, 임의로 바꾸지 말고 **diff/대안을 제시한 뒤 확인**을 받습니다.
* 큰 변경이 불가피하면 변경 전 상태를 보존(예: 백업 또는 git으로 추적)한 뒤 진행합니다.
* `.gitignore`는 기존 항목을 유지한 채 부족한 항목만 추가합니다.

# 6. 채택 중 사용자에게 질문해야 하는 경우

브라운필드 특화 기준입니다. (그 외 일반 기준은 `KICKOFF.md` 2.1을 따릅니다.)

* 코드와 의도가 충돌하는데 **어느 쪽이 권위인지 합리적으로 판단할 수 없는** 경우
* **기존 산출물 파일을 덮어쓰거나 크게 바꿔야** 하는 경우 (반드시 확인)
* `SOURCES/REQUIREMENTS.md`의 요구사항이 **현재 구현과 명백히 충돌**하는 경우
* 코드 수정이 필요해 보이지만 이 단계 범위(문서화)를 벗어나는 경우 → 수정하지 말고 남은 작업으로 기록·확인
* 민감정보/개인정보/보안에 영향을 줄 수 있는 구조가 발견된 경우

`[AI 위임]` 마커 처리는 `KICKOFF.md` 2.4와 동일합니다.

# 8. 완료 조건

`KICKOFF.md` 17절의 완료 조건을 만족하되, 다음 브라운필드 조건을 추가로 만족해야 합니다.

* 구현된 기능이 **as-built 명세**로 문서화됨
* as-built 명세가 **실제로 읽은 코드에 근거**하며, 각 동작 주장에 근거 코드 위치를 댈 수 있음
  (직접 읽지 않은 동작은 단정하지 않고 "추정(검증 필요)"으로 표시됨)
* **읽은 범위 / 읽지 못한 범위**가 명시되고, 미열람 영역은 PROGRESS.md에 남겨짐
* **코드 ↔ 의도 괴리 목록**이 정리되어 HISTORY/ASSUMPTIONS/feature 15절에 기록됨
* 기존 테스트의 **실행 baseline**이 HISTORY.md에 기록됨
* 기존 산출물 파일이 **덮어쓰기 없이 병합**되었거나, 덮어쓰기가 필요한 경우 사용자 확인을 거침
* `ARCHITECTURE.md`가 코드에서 **역추출**되었고, 추정 항목이 ASSUMPTIONS에 명시됨
* `PLAN.md`가 **현재 상태(완료/진행 중/남은 것)** 를 반영함
* 이 단계에서 **코드를 수정하지 않았음**(문서화·계획만)
* 채택 산출물이 **작업 브랜치에 commit됨** (문서 전용 commit — 코드 변경 없음; 여러 세션에 걸친 채택이면 중간 commit 허용)
