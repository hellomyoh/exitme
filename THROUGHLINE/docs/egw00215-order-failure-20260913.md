# 2026-09-11 09:01 발주 실패 분석 — EGW00215(원장 초당 한도)로 그날 매수가 통째로 생략된 건 (2026-09-13)

사용자 화면 기록: `M-한투-ETF` 의 무인 그리드 1·2·3차 매수 3줄이 모두 **생략**, 사유는
`잔고 조회 실패로 발주하지 않았습니다 — KIS error EGW00215 원장에서 허용 가능한 초당 거래건수를 초과하였습니다`.
같은 09:01 에 `J-한투-Tiger` 의 축소·익절 매도와 `M-한투-ETF` 의 익절 매도는 `무인 매도 꺼짐 — 수동 처리` 로,
이쪽은 오류가 아니라 계좌 플래그(매도 off) 때문이다.

## 1. 무엇이 일어났나 — 세 겹의 원인

| 층 | 코드 | 당시 동작 |
|---|---|---|
| ① 유량 코드 판정 | `kis_client._get` | 500 응답의 `msg_cd` 가 **EGW00201 이 아니면 즉시 오류**로 올렸다. EGW00215 는 재시도 대상이 아니었다 |
| ② 실패 파급 | `autoexec._place_lines` ④ | 잔고 조회가 실패하면 그 계좌의 **남은 줄 전부**를 생략한다 (원장 대조 없이는 발주하지 않는다는 안전장치) |
| ③ 복구 부재 | `autoexec.run_watchdog` | 09:15 감시는 **"09:01 실행 기록이 없는"** 포트만 지연 실행한다. 이 포트는 "실행함(생략 3건)"이라 건너뛰었다 |

세 개가 겹쳐 **조회 한 번의 일시적 거절이 그날 그 계좌의 매수 전부**가 됐고, 사용자가 화면에서 `재시도` 를
누를 때까지 아무도 다시 내지 않았다. 09:01 에 한 번 실패하면 하루가 비는 구조였다.

## 2. 왜 그 순간 한도를 넘었나

EGW00201 과 EGW00215 는 **다른 층의 한도**다.

- **EGW00201** — 게이트웨이(앱키) 단위 초당 거래건수. 2026-09-09 사고 뒤 Redis 공용 카운터로 앱키·환경별
  초당 10건(실전)/1건(모의)으로 묶어 두었다.
- **EGW00215** — "원장에서 허용 가능한 초당 거래건수". 계좌 **원장** 쪽 한도라 앱키 카운터로는 막히지 않는다.

09:01 배치는 국내 포트를 id 순으로 돌며 계좌마다 `시가 1 + 잔고 1 + (줄마다 매수가능 1 + 주문 1)` 을 연속으로
부른다. 포트 사이 간격은 1초(`PORTFOLIO_GAP_SEC`)지만 **한 포트 안에서는 원장 호출이 0.15초 간격으로 몰린다**.
같은 계좌를 두 포트가 쓰거나, 장중 재시도·체결 동기화가 겹치면 원장 한도를 넘기 쉽다. 화면 기록에서
`J-한투-Tiger` 처리 직후 `M-한투-ETF` 잔고 조회가 거절된 것이 이 모양이다.

## 3. 조치

| # | 조치 | 파일 |
|---|---|---|
| 1 | **EGW00215 를 유량 코드로 인정** — EGW00201 과 같이 1·2·4·8초 백오프 재시도(GET 4회, 주문 POST 3회). 주문 POST 는 "KIS 가 접수 전에 거절"한 경우라 중복 위험이 없다는 기존 논리가 그대로 적용된다 | `services/kis_client.py` |
| 2 | **원장(계좌) 단위 초당 카운터 추가** — 앱키 버킷과 별개로 `계좌번호` 버킷을 두고 실전 2건/초·모의 1건/초로 제한. 잔고·매수가능·체결·미체결·예약 조회와 모든 주문 POST 가 대상(시세 조회는 아님). Redis 가 없으면 인스턴스 단위 0.4초 최소 간격으로 대체 | `services/kis_client.py` |
| 3 | **200 + `rt_cd≠0` 형태의 유량 초과도 재시도** — KIS 가 같은 오류를 두 가지 형태로 준다 | `services/kis_client.py` |
| 4 | **09:15 감시가 일시적 생략을 다시 낸다** — 생략 사유가 조회 실패(`skip_cause="api"`)인 줄과, 발주 실패인데 사유가 유량 초과인 줄만 골라 09:01 과 같은 절차로 재발주. 갭 취소·플래그 꺼짐·잔고 부족·상한·사전 대조 불일치는 그날의 판정이므로 대상 외 | `autoexec.py` |
| 5 | 사용자 메시지에 EGW00201·EGW00215 안내 추가 | `broker.py` |

4번이 다시 내는 줄은 **접수된 적이 없는 줄**뿐이라 중복 발주가 되지 않는다(생략 = 발주 시도 없음, 유량 거절 =
KIS 가 받기 전 거절). 재시도는 기존 `retry_auto_exec` 경로를 그대로 쓰므로 시가·갭·잔고 대조·상한·매수가능을
다시 통과해야 나간다.

## 4. 남는 위험·한계

- **지정가 줄은 09:01 과 같은 가격, 시장가 줄은 09:15 시세로 나간다.** 그리드·익절은 지정가라 영향이 없지만
  축소·레버리지 시장가 줄은 09:01 에 냈을 때와 체결가가 다르다. 사용자가 직접 누르던 `재시도` 와 같은 성질이며,
  09:15 자동화는 이 점을 감수한 선택이다 — 원치 않으면 4번만 되돌릴 수 있다(감시 함수 한 줄).
- KIS 는 EGW00215 의 정확한 임계를 공개하지 않는다. 2건/초(실전)는 관측이 아니라 **보수적 가정**이다.
  실제 임계가 더 낮으면 재시도(1번)가 받아 주고, 더 높으면 배치가 조금 느려질 뿐이다.
- 실계좌 재현은 하지 않았다(유량 초과를 일부러 내야 한다). 검증은 응답을 흉내 낸 단위·통합 테스트로 했다.
- 09:01 총 소요는 계좌·줄 수에 비례해 늘어난다. 계좌 1개·줄 4개 기준 원장 호출 10건 ≈ 5초로, 09:15 감시·
  09:30 지연 상한 안에 충분히 들어온다.

## 6. 함께 확인한 것 (오류 아님)

`무인 매도 꺼짐 — 수동 처리` 3줄은 `J-한투-Tiger`·`M-한투-ETF` 계좌의 **매도 플래그가 꺼져 있어서**다.
09:01 에 축소·익절 매도가 필요하다고 판정됐지만 발주하지 않고 수동으로 남겼다는 뜻이다. 설정 › 무인 실행에서
계좌별로 매도를 켜면 같은 줄이 자동 발주된다.
