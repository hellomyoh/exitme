## 1. 주문표 레짐이 하루 늦다 — 사실

### 1.1 경로 확인

`plan()` 은 `prev_regime` 을 받아 **기준일 종가로 새 레짐을 정하고**(`planner.py:179`) 그것으로 주문을 만든 뒤
`Plan.regime` 에 담아 돌려준다(`planner.py:386`). 그런데 `signals.py` 는 **입력한 쪽**을 응답에 싣는다.

```
signals.py:239   regime = Regime(result.regimes[-1])   # 기준일 전날 종가로 정한 값
signals.py:326   p = plan(last, m200, mlev, regime, …)  # p.regime = 기준일 종가로 정한 값 ← 주문은 이걸로 만들어진다
signals.py:367   "regime": regime.value                 # ← 입력을 싣는다 (하루 늦음)
signals.py:371   regime_view.detail(regime.value, …)    # ← 같은 값
signals.py:397   payload = {"regime": regime.value, …}  # ← 동결 스냅샷·체결 태그용
```

표시로 끝나지 않는다. 이 payload 가 발주 행의 계획 레짐이 되고, 체결 가져오기가 그 값으로 로트를 정한다.

```
autoexec.py:909  plan_regime=plan.get("regime")          broker.py:850  plan_regime=payload["regime"]
broker.py:421    lot_tag(bo.kind, "buy", bo.plan_regime, …)
lots.py:36       if plan_regime == "BULL" and f1_no_tp_in_bull → core(익절 없음), 아니면 grid + 익절가
portfolios.py:199 화면의 체결 등록도 같은 값을 받는다
```

백테스트는 `regime = p.regime` 로 갱신한 **뒤** 체결을 태그한다(`backtest.py:207·257·287`). 그래서 전환 다음 날
체결의 분류가 실전과 백테스트에서 반대로 붙는다. 소급 스크립트는 `plan_day_context` 로 **체결일 키의 레짐**
(= 계획일 종가에 결정된 값)을 쓰므로 백테스트와 같다 — **두 태그 원천이 서로 다르다**는 지적도 맞다.

### 1.2 보고서보다 좁은 점 — `rebuild_lots` 는 이 값을 쓰지 않는다

`signals.py:310` 이 `rebuild_lots(…, regime.value)` 로 넘기지만, **`regime_now` 인자는 함수 본문에서 한 번도
쓰이지 않는다**(선언만 있고 미사용, 확인함). 로트 재구성은 `reg_by_date`(체결일 키 — 올바른 원천)로만 전환을
재생한다. 따라서 하루 늦은 레짐이 **로트 재구성에는 닿지 않는다.** 고칠 표면은 표시 3곳 + `plan_regime` 1곳이다.

### 1.3 고칠 때 건드리면 안 되는 지점 — 전환 재생의 끝점

`rebuild_lots` 의 `while i < last` 는 **기준일 종가 전환을 재생하지 않는다.** 이게 맞다. 백테스트도
`plan(i)` 를 **먼저** 부르고 그 뒤에 `apply_regime_conversion` 을 적용한다(`backtest.py:191→206`) — 전환일 주문은
**전환 전 로트 상태**로 만들어진다. "레짐을 새 값으로 바꾸는 김에 로트 전환도 기준일까지 당기자"는 수정은
**백테스트와 새로 어긋나게 만든다.** 표시·`plan_regime` 만 바꾸고 재생 끝점은 그대로 두어야 한다.

## 2. 시뮬레이터 레짐 미워밍업 — 사실

`backtest.py:164` 가 `regime = Regime.NEUTRAL` 로 시작하고 루프는 `first = start_index` 부터 돈다. 지표는
이전 봉으로 준비되지만(`prepare`) **레짐 상태 기계만 시작일에 중립에서 새로 출발한다.** 레짐 판정에 완충
구간(`regime_buffer`·`ma200_exit_buffer`)이 있어 히스테리시스가 걸리므로, 시작일이 완충 안이면 전체 이력을
돌린 값과 갈린다.

### 재현 (94개 시작점, 20거래일 간격, 각 1년)

| 항목 | 측정값 | 보고서 |
|---|---|---|
| 첫날 레짐이 전체 이력과 다른 시작점 | **12개 / 94 (13%)** | 11개 / 91 (12%) |
| 같아질 때까지 | 중앙 **7거래일** · 최대 **18거래일** | 중앙 9 · 최대 18 |
| 1년 수익률 차이 (콜드 − 워밍) | 중앙 **−0.6%p** · 범위 **−5.2 ~ +2.5%p** | 중앙 −1.7%p · 범위 −6.3 ~ +2.8%p |

갈리는 사례는 전부 **완충 구간**이다 — 시뮬 NEUTRAL vs 전체이력 BEAR(2018-02-27 · 2018-09-20 · 2019-07-18 ·
2022-01-19), 시뮬 NEUTRAL vs 전체이력 BULL(2021-04-01 · 2021-05-31).

### 판정 근거는 수익률이 아니다

수익률 차이는 중앙 −0.6%p 로 [노이즈 밴드](validation-methodology-20260913.md) 안이고 부호도 양쪽으로 갈린다.
**고쳐야 하는 이유는 성과가 아니라 재현성이다** — 시뮬레이터는 "이 전략을 실전에 걸면 어떻게 되나"를 보려고 쓰는데,
지금은 실전이 쓰는 레짐과 다른 레짐으로 답한다. 시뮬 기본 기간이 최근 1년이라 **이 경우가 기본 상태**라는 지적도 맞다.

### 구현 시 주의

`next_regime` 은 MA200 을 요구하므로 상태 기계는 **지표가 채워진 첫 봉부터** 돌려야 한다(그 이전은 NEUTRAL 유지).
워밍업이 260봉이라 최대 수렴 18거래일보다 충분히 길다. 레짐은 가격만의 함수라 비용은 봉당 `next_regime` 한 번이다.

## 3. 숫자가 보고서와 다른 점

같은 방향·같은 규모지만 정확히 일치하지는 않는다(전환 41회는 일치). 창 길이·시작점 격자·워밍업 경계가 다르면
생기는 차이로 보이며, **결론을 바꾸지 않는다.** 이 문서의 숫자는 위 스크립트로 재현 가능하다.

## 4. 권고

순서는 보고서 제안대로 **② 먼저, ① 다음**이 맞다 — ②는 백테스트 엔진 안에서 끝나고, ①은 그 엔진이 내는
레짐을 어디에 싣느냐의 문제라 ②가 고쳐진 뒤에 보는 편이 안전하다.

- **②**: 워밍업 구간에서 레짐 상태 기계도 함께 돌린다. 지표가 채워진 첫 봉부터. 기존 재현성 테스트가 **끝을 잘라내는
  경우만** 검사해 못 잡았으므로, **앞을 잘라내는** 동일성 테스트를 함께 넣는다.
- **①**: 응답·`regime_detail`·스냅샷·`payload["regime"]` 를 `p.regime` 으로 바꾼다. 플래너 **입력만** 이전 레짐으로 둔다.
  `rebuild_lots` 의 전환 재생 끝점(`i < last`)은 **건드리지 않는다**(§1.3). 전환일 체결 태그가 백테스트·소급 스크립트와
  같은지 확인하는 테스트를 함께 넣는다.
- 기존 발주 행의 `plan_regime` 소급 교정은 **별건**이다. 이 계좌는 9월에 전환이 없어 영향이 없다(보고서와 일치).

## 5. 레짐 전수조사 (2026-09-15 지시 1) — 어긋남이 닿는 곳과 닿지 않는 곳

`regime` 을 만들고 쓰는 모든 지점을 훑었다. 원천은 셋뿐이다.

| 원천 | 값의 의미 |
|---|---|
| `result.regimes[k]` (`out_dates[k]` 와 짝) | **그 실행일을 지배하는 레짐** = 계획일 종가에 결정 — 정본 |
| `Plan.regime` | 기준일 종가로 정한 값 = 그 주문표의 실행일 레짐 — 위와 같은 것 |
| `signals.py:239` `Regime(result.regimes[-1])` | **기준일**을 지배한 레짐 = 플래너 입력 (하루 이르다) |

### 틀린 곳 (전부 세 번째 원천이 샌 자리)

| 위치 | 무엇 | 파급 |
|---|---|---|
| `signals.py:367` | 주문표 응답 `regime` | 대시보드·주문표 화면 |
| `signals.py:371` | `regime_detail` | **기준일 지표로 전날 레짐을 설명**한다 — 자기모순 |
| `signals.py:397` | `payload["regime"]` (동결) | ↓ 아래 넷의 상류 |
| `portfolios.py:825` | 일자별 일지 `regime` | 화면 |
| `autoexec.py:909` | `BrokerOrder.plan_regime` (09:01) | **체결 태그** |
| `broker.py:850` | 예약주문 `plan_regime` | **체결 태그** |
| `portfolios.py:199` | 화면 체결 등록(`body.plan_regime`) | **체결 태그** |
| `signals.py:609~614` | 포트 응답이 `snap.regime` 을 덮어씀 | 같은 화면에서 **모델 기준은 맞고 포트 기준만 틀림** |

`broker.py:421` 이 `lot_tag(…, bo.plan_regime, …)` 로 로트를 정하므로, 위 셋이 전환 다음 날 코어/그리드를 뒤집는다.

### 맞는 곳 (건드리지 않는다)

- `signals.py:149` 공용 모델 일일 스냅샷 — `last_plan.regime.value` 로 **이미 옳다**
- `signals.py:492·524·565` **미국(TF) 경로 — 이미 `lp.regime` 을 쓴다.** 국내 포트 경로만 어긋나 있었다
- `signals.py:460·654`, `backtests.py:313·364`, `worker.py:333` 백테스트 시계열 — 정본 그대로
- `signals.py:326` 플래너 입력 — 이전 레짐이 **맞다**
- `lots.py` `plan_day_context` (소급 스크립트) · `rebuild_lots` 의 전환 재생과 끝점 — §1.3
- `signals.py:310` 이 넘기는 `regime_now` — `rebuild_lots` 가 **읽지 않는다**(문서화함)
- `settings.py:30` 은 `regime_buffer` 파라미터 이름일 뿐 무관

**결론: 어긋남은 국내 포트 주문표 한 경로에서만 새어 나왔고, 그 한 값이 화면 3곳과 체결 태그 3경로로 퍼졌다.**
다른 계산(백테스트·모델 스냅샷·미국 경로·소급 스크립트)은 처음부터 옳았다.

## 6. 구현 (2026-09-15 지시 2)

**② 워밍업** — `backtest.warm_regime(m200, params, upto)` 를 추가하고 `regime = Regime.NEUTRAL` 을 대체했다.
`plan()` 의 워밍업 가드와 **같은 조건**을 쓰므로 전체 이력을 처음부터 돌린 것과 같은 상태가 나온다.
재측정: 첫날 레짐이 다른 시작점 **12개 → 0개**.

**① 하루 어긋남** — `plan_regime = p.regime if p.status == "OK" else regime` 을 두고 응답·`regime_detail`·
`payload` 세 곳에 실었다. 플래너 입력은 그대로 이전 레짐이다. `rebuild_lots` 는 **손대지 않았다**(§1.3).

**테스트**
- `test_backtest_started_midway_warms_the_regime_state_like_the_full_run` — 앞을 잘라낸 실행의 레짐이 전체 실행과
  같은지. 기존 R2 는 **끝만** 잘라 봐서 못 잡았다. 수정을 되돌리면 실제로 실패하는 것을 확인했다("시작 300: 첫날 레짐이 다르다").
- `test_the_regime_frozen_on_the_plan_is_the_one_the_tag_sources_use` — **plan.regime == reg_by_date[실행일]
  == plan_day_context(실행일)** 항등식. 전환이 0회면 실패하도록 해 테스트가 무의미해지지 않게 했다.
- `test_signals` 포트 기준 응답의 `regime` 이 공용 모델 기준과 같은지 — 같은 실행일을 가리키므로 같아야 한다.

이 계좌는 9월에 전환이 없어 영향이 없다.
