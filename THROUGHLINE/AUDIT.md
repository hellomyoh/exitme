# AUDIT.md

프로젝트 문서와 코드의 표류(drift)를 주기적으로 점검하는 **문서 감사 프롬프트**입니다.

새 가정 기록 시 충돌 점검 같은 "기록 시점 점검"은 KICKOFF/DEVELOPINIT에 이미 있습니다.
그러나 세션이 쌓이면서 생기는 점진적 표류 — 완료됐는데 갱신 안 된 PLAN, 폐기됐어야 할 active 가정,
코드와 조금씩 어긋난 feature 명세, 누락된 인덱스 항목, 끊어진 문서 링크 — 는
기록 시점 점검만으로는 잡히지 않습니다. AUDIT는 이를 주기적으로 회수합니다.

> **경로 기준:** 프레임워크 문서는 루트 3파일(프로젝트 `README.md`, `AGENTS.md`, `CLAUDE.md`)을 제외하고
> 모두 `THROUGHLINE/` 폴더 안에 있습니다. 이 문서의 산출물 경로는 모두 `THROUGHLINE/` 기준입니다.
> 감사 시 산출물이 THROUGHLINE/ 밖에 생성되어 있지 않은지도 함께 점검하세요.

---

# 1. 실행 시점

다음 중 하나에 해당하면 실행을 권장합니다.

* Phase가 완료된 직후
* 릴리즈 / 배포 전 (`qa/release-checklist.md`와 함께)
* 오랜만에 프로젝트를 재개할 때
* 마지막 감사 이후 세션이 약 10회 이상 누적되었을 때
* 문서와 실제 동작이 어긋난다고 의심될 때

---

# 2. 감사 원칙

1. **이 단계에서는 기능 코드를 수정하지 않습니다.** 감사는 점검·기록 단계입니다.
2. **기계적 불일치는 즉시 고칩니다.** 인덱스 누락, 끊어진 링크, 상태 표기 누락처럼
   판단이 필요 없는 항목은 감사 commit에서 바로 수정합니다.
3. **의미적 표류는 고치지 않고 기록합니다.** 코드↔명세 불일치는 DEVELOPINIT 3.4(권위 진단)의
   대상이므로, 여기서는 발견 사실만 기록하고 처리는 개발 작업으로 분리합니다.
4. **감사도 작업입니다.** 결과를 HISTORY.md에 `audit` 항목으로 기록합니다.

---

# 3. 감사 항목

## 3.1 계획 vs 실제 (PLAN / PROGRESS)

* PLAN.md의 Phase 상태가 HISTORY.md·실제 코드와 일치하는가
* 완료 표시된 Phase의 완료 조건(테스트 실제 실행 포함)에 HISTORY.md상 근거가 있는가
* PROGRESS.md의 "다음 세션 첫 명령"이 현재 상태와 맞는가

## 3.2 가정 수명 (ASSUMPTIONS)

* `상태: active`인 가정 중 이미 사용자 답변/ADR/구현으로 확정·폐기됐어야 할 것
* 서로 충돌하거나 ARCHITECTURE.md와 어긋나는 가정

## 3.3 명세 vs 코드 (features / ARCHITECTURE) — 샘플링

* 최근 변경이 많았던 feature 문서 1~3개를 골라 명세와 실제 코드를 대조
* ARCHITECTURE.md의 계약(네이밍 / 에러 포맷 / 인증 등)이 최근 코드에서 지켜지는지 샘플 점검
* 불일치는 여기서 수정하지 말고 기록만 합니다(원칙 3)

## 3.4 인덱스 무결성

* `features/README.md`에 모든 feature 문서가 올라가 있고 상태가 정확한가
* `adr/INDEX.md`에 모든 ADR이 있고 상태가 정확한가
* `docs/README.md`가 docs/ 폴더의 실제 파일과 일치하는가

## 3.5 링크 / 고아 문서

* 문서 간 상대경로 링크 중 끊어진 것
* 어떤 인덱스에서도 참조되지 않는 고아 문서

## 3.6 이력 / 노트 위생

* HISTORY.md 회전 필요 여부 (KICKOFF.md 14절 기준)
* HISTORY 항목이 고정 접두사 형식(`## [YYYY-MM-DD] <type> | <제목>`)을 따르는가
* NOTES.md에 ASSUMPTIONS로 가야 할 추측이 섞여 있지 않은가 (사실/가정 구분)

## 3.7 프로젝트 README

* README의 설치 / 실행 / 구조 설명이 현재 코드와 맞는가 (표본 확인)

## 3.8 제출 자료 (SOURCES)

* `미반영` / `검토 중` 상태로 방치된 항목이 있는가
  (특히 변경요청 — 사용자 의도가 산출물에 반영되지 않은 채 잠들어 있는 상태)
* SOURCES/INDEX.md와 실제 파일 목록이 일치하는가 (미등재 파일 / 사라진 파일)
* `반영 완료` 항목의 산출물 링크가 유효한가
* `반영 완료` 이후 원본이 수정되지 않았는가 (불변 원칙 위반 — git 이력으로 확인)

## 3.9 항상 로드 문서 비대화

* **PLAN 완료 Phase 회전 (기계적):** PLAN.md의 완료 상태 Phase가 **4개를 초과**하면
  KICKOFF.md 12절 회전 규칙에 따라 오래된 완료 Phase를 `PLAN-archive.md`로 이관합니다
  (감사 commit에 포함 — 즉시 수행). 중복 구현 방지·완료 Phase 재수행 금지에 필요한 정보를
  잃지 않는 선에서 수행합니다.
* **ARCHITECTURE 배경 잔존 (관찰):** ARCHITECTURE.md에 계약 선언이 아닌 배경 설명·폐기된
  과거 계약이 잔존하면 **다이어트 후보로 보고서에 표시만** 합니다. 여기서 ARCHITECTURE를
  임의로 압축하지 말고(판단 필요), 폐기 계약은 ADR(Deprecated/Superseded)로 옮길지 사용자와 결정합니다.

## 3.10 검토 로그 (discussion) — 표본 점검

* 비자명한 feature 문서에 검토 로그 링크가 있는가 (없으면 검토 누락 의심)
* 표본 1~2개 로그를 열어 **출처 의무**가 지켜졌는가 — 특히 Research Agent의 웹 출처가
  **전체 URL로 로그에 보존**됐고(축약·문서명만이 아님) 그 URL이 **실재하는가** (없거나 축약된 출처 = 검토 위조·검증불가 신호)
* **실행 방식**이 enum(`role-play` / `parallel-subagents` / `parallel-external`) 중 하나인가, `parallel-*`이면
  서브에이전트별 증거(식별자·입력 범위·출력 요약)가 있는가 — 증거 없는 병렬 주장, 또는 환경 능력과 모순되는
  표기(서브에이전트 불가 환경)는 실행 방식 위조 신호
* 로그가 KICKOFF.md 4.1의 구조(페르소나별 검토 / 쟁점 / 결론)를 따르는가, 일반론만 나열된 연극성 로그는 아닌가
* 로그의 참여 페르소나가 `personas/`에 인스턴스로 실재하고 INDEX와 일치하는가
* 페르소나 인스턴스가 지식 복사 없이 링크·체크리스트만 담고 있고, **특화 하한**(프로젝트 고유 링크 3개 이상 —
  KICKOFF.md 5.2 규칙)을 충족하는가
* 최근 횡단 계약 변경(ADR) 이후 페르소나 체크리스트가 **낡지 않았는가**(폐기된 계약을 여전히 참조하는 항목)?
  최근 ADR과 대조해 인스턴스 1~2개를 표본 점검하고, 낡은 항목은 보고서에 갱신 후보로 나열 (갱신 자체는 후속 작업)
* 로그 결론의 모든 쟁점에 상태(`resolved` / `deferred` / `requires user decision` / `requires ADR`)가 붙어 있는가,
  `resolved`가 아닌 쟁점이 feature 문서("남은 쟁점"/15번)에 드러났는가, QA/Security의 실패 조건이
  12번 또는 qa/에 반영됐는가 (위험→테스트 추적 — KICKOFF.md 4.1)
* 어떤 feature에서도 링크되지 않는 고아 로그가 있는가

## 3.11 백로그 (TODO)

* `대기` 상태로 장기 방치된 항목이 있는가 (예: 60일 이상 — 승격/보류/폐기 재분류 후보로 보고)
* `승격` 항목의 승격처 링크가 유효한가
* 승격처 작업이 완료됐는데 TODO 상태가 `완료`로 갱신되지 않은 항목이 있는가
* TODO에 명세 수준의 상세 내용이 적혀 있지 않은가 (명세는 features/로 — KICKOFF.md 15.3 역할 경계)

## 3.12 산출물 언어 일관성 — 표본 점검

* 표본 문서(feature/docs 각 1~2개)의 서술 산문이 규정 언어(SOURCES/REQUIREMENTS.md의 주 언어 또는
  지정된 "산출물 작성 언어")로 일관되는가
* 한 문서 안에서 절(섹션)에 따라 산문 언어가 바뀌는 혼용이 없는가
  (코드 식별자·API 경로·코드 블록·기술 고유명사의 영어는 정상 — 혼용이 아님)
* 혼용 발견 시 수정하지 말고 다이어트 후보처럼 보고서에 표시하고, 정리는 별도 문서 작업으로 분리

# 4. 처리 규칙

| 발견 유형 | 처리 |
|---|---|
| 인덱스 누락 / 끊어진 링크 / 상태 표기 오류 | 즉시 수정 (감사 commit에 포함) |
| 확정/폐기됐어야 할 가정 | 근거가 명확하면 상태 갱신, 불명확하면 "검증 필요"로 기록 |
| 코드↔명세 불일치 | 수정하지 않고 발견 목록에 기록 → DEVELOPINIT 3.4로 처리할 작업으로 분리 |
| HISTORY 회전 필요 | 즉시 수행 가능 (KICKOFF.md 14절 규칙) |
| PLAN 완료 Phase 회전 필요 (4개 초과) | 즉시 수행 가능 (KICKOFF.md 12절 규칙 — PLAN-archive.md 이관) |
| ARCHITECTURE 계약 위반 코드 | 기록만, 수정은 개발 작업으로 |
| 방치된 미반영/검토 중 변경요청 | PROGRESS.md 남은 작업에 등재하고 보고서에 명시 |
| 검토 로그 누락 / 출처 미실재 / 연극성 로그 / 증거 없는 병렬 주장 | 해당 feature의 재검토를 후속 작업으로 분리하고 보고서에 명시 |
| 반영 완료 원본의 사후 수정 (불변 위반) | 임의로 되돌리지 않고, 수정분을 새 요청 문서로 분리할지 사용자 확인 |
| 판단 불가 항목 | "사용자 확인이 필요한 사항"에 정리 |

감사에서 생긴 후속 작업은 PROGRESS.md의 `남은 작업`(필요 시 PLAN.md)에 반영하고,
감사 결과 전체를 HISTORY.md에 `## [YYYY-MM-DD] audit | 문서 감사` 항목으로 기록합니다.
기계적 수정과 감사 기록은 하나의 commit으로 묶습니다 (`docs/...` 작업 브랜치 사용,
main/master 직접 push 금지는 동일하게 적용).

# 5. 출력 형식

감사 완료 후 다음 형식으로 보고하세요.

```md
# 문서 감사 결과

## 감사 범위 / 샘플링 기준

## 즉시 수정한 항목 (기계적)

## 발견된 표류 (처리 필요)

- 코드↔명세 불일치:
- 가정 수명 문제:
- 계획↔실제 불일치:

## 인덱스 / 링크 상태

## 제출 자료(SOURCES) 상태

## HISTORY / NOTES 위생

## 항상 로드 문서 비대화 (PLAN 완료 Phase 수 / ARCHITECTURE 배경 잔존 여부)

## 검토 로그 표본 점검 결과 (출처 실재 / 실행 방식 증거 / 위험→테스트 추적)

## 백로그(TODO) 상태 (방치/링크/완료 미반영)

## 산출물 언어 일관성 (표본 결과)

## 사용자 확인이 필요한 사항

## 후속 작업 제안 (PROGRESS.md 반영 내용)
```

* 기계적 불일치 즉시 수정 및 commit
* 의미적 표류가 발견 목록으로 정리되고 PROGRESS.md에 반영됨
* HISTORY.md에 `audit` 항목 기록
* 5절 형식으로 보고
